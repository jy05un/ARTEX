# HTTP 请求走私 — 授权测试方法论

> **授权前提**：仅在授权目标上以**自有请求**验证前后端对报文边界解析的不一致。禁止投放会被拼接到**真实用户**请求上的恶意前缀（缓存投毒、劫持他人会话、注入他人响应）；确认以“证明前后端解析不一致”为止，有危害的利用走审批。

## 快速流程

1. 识别存在前端代理 + 后端的架构（CDN/LB/反代）。
2. 用区分型探针检测 CL/TE 处理差异。
3. 以计时/响应差异确认走私通道存在。
4. 评估风险（缓存投毒、前缀劫持）但不对真实流量实施。
5. 记录 PoC，给出统一解析/升级 HTTP 的修复建议。

## 探测类型

- **CL.TE**：前端按 `Content-Length`、后端按 `Transfer-Encoding: chunked`。
- **TE.CL**：相反。
- **TE.TE**：双方都支持 TE，但可用混淆头（`Transfer-Encoding : chunked`、重复头、大小写）让一方忽略。
- **H2.CL / H2.TE**：HTTP/2 降级到 HTTP/1.1 时的长度歧义。

用差异化探针观察“前端认为请求结束、后端还在等/多读”的**时间延迟**或响应错位作为判据（经典的 timing-based 检测），且探针只影响**自己后续发出的请求**。

## 影响评估（不实施于真实流量）

缓存投毒、绕过前端访问控制、捕获他人请求、响应队列错位——在报告中说明可达危害，**不**对真实用户请求做拼接/投毒验证。

## 修复建议

前后端使用一致且严格的报文解析；拒绝同时含 CL 与 TE、或畸形 TE 的请求；前端规范化后再转发；尽量全链路 HTTP/2 且禁用有歧义的降级。

## 边界与禁止

| 禁止 | 替代 |
|---|---|
| 缓存投毒影响其他用户 | 仅用自有请求证明解析不一致 |
| 捕获/劫持真实用户请求或会话 | 时序差异确认通道存在即止 |
| 持续注入污染共享缓存 | 不触碰共享缓存，必要验证走审批 |
