# 游戏客户端安全评估（负责任披露导向）

> **授权前提（硬性）**：仅在书面授权或厂商 SRC 明确接收范围内、使用**测试账号**进行。本 skill 的终点是**证明"服务端缺少对客户端值的校验"这一设计缺陷并上报**，不是取得利益。**禁止**：实际修改真实余额/充值/购买记录、真实复制或获取物品、变更真实订单的货币类型、公开或传播 PoC/工具、在他人账号上操作。任何会使账号真实获益或造成不可逆改变的动作一律不做——改用"仅观察请求结构 + 说明缺失的校验"来证明。先确认目标游戏 EULA/当地法律是否允许客户端逆向。

## 核心判据：信任边界

绝大多数"刷币/免费物品/改货币"类问题的**根因都是同一个**：客户端把本应由服务端权威计算的值（金额、价格、货币种类、物品 id、数量）当作可信输入发给服务端，而**服务端未做校验**。本评估就是定位这个信任边界，**证明它存在**，而不是去跨过它获益。

## 快速流程（观察 → 证明 → 报告）

1. **环境隔离**：在隔离的测试机/虚拟机上用测试账号运行，记录初始状态（截图余额/物品，用于证明"未实际变更"）。
2. **协议观察**：被动抓取客户端↔服务端流量，看关键操作（购买、兑换、领取、充值回调）的请求里**是否出现客户端可控的金额/价格/货币/物品字段**。
3. **校验探测（只读/非获益）**：判断服务端是否校验这些值——用**不产生真实获益**的方式证明，例如：
   - 请求是否缺少对金额/价格的服务端签名或重算；
   - 是否无幂等键（可重放领取类操作的结构，但**不实际重放到获益**）；
   - 物品 id/货币类型是否由客户端决定且无归属/合法性校验。
4. **结构化证明**：用请求/响应样本 + 字段说明，论证"若篡改 X 字段，服务端会接受"——以**协议结构和缺失的控制**为证据，而非真的完成一笔欺诈交易。
5. **立即上报**：按补天模板撰写报告，附复现思路、影响评估、修复建议。测试后恢复/保留初始状态证据。

## 观察手段（被动为主）

- **网络层**：代理/抓包观察明文或可解密流量（若 TLS，检查是否可在测试机上做合法的本地 MITM 以观察自有流量结构）。重点看字段，不看就改。
- **客户端静态分析**：理解封包格式、字段含义、是否有客户端侧"伪校验"（可被忽略的本地检查即说明服务端未权威校验）。用于**理解协议**，不用于制作外挂。
- **状态对比**：对比"正常操作"的请求，识别哪些值来自客户端。

## 如何"证明而不获益"

| 想证明的问题 | 获益式做法（禁止） | 负责任做法（采用） |
|---|---|---|
| 金额/价格客户端可控 | 真发一笔 1 元买 1000 元商品并下单成功 | 展示购买请求含客户端 `price` 字段、响应未重算；说明缺签名/重算 |
| 货币种类可换 | 真把扣费货币从付费币改成免费币完成购买 | 展示请求中 `currency` 字段客户端可控且无服务端绑定校验 |
| 任意领取物品 | 真领取并获得物品 | 展示 `item_id`/数量客户端决定、无归属/上限校验的请求结构 |
| 重放领取 | 重放到真实到账多份 | 说明无幂等键/nonce；至多在**不到账**层面说明结构 |

> 若厂商在复现时明确要求"必须完成一次以证明可利用"，这属于**需厂商书面同意**的升级动作，由人在环路审批后，做**单次、最小、可回滚**的协调演示，并立即配合回退。默认不做。

## 报告要素（补天/SRC）

- 漏洞类型：建议归类为"作弊漏洞"或业务逻辑/越权（按平台类别）。
- 复现：抓包样本（脱敏）、涉及字段、服务端缺失的校验点。
- 影响：经济系统可被操纵的范围与后果（说明性，非实证获益）。
- 修复建议：见下。
- 证据：初始/结束状态截图，证明测试未造成真实获益或已回退。

## 修复建议（给厂商）

服务端对金额、价格、货币种类、物品归属与数量**权威计算与校验**，不信任客户端传入值；关键操作加幂等键/nonce 防重放；购买/充值走服务端订单与回调签名校验；客户端校验仅作体验优化，绝不作为唯一防线；异常值与频率风控告警。

## 边界与禁止

| 禁止 | 替代 |
|---|---|
| 实际改余额/充值/购买记录、真领物品、换真实货币 | 只证明协议结构缺校验，状态不获益 |
| 制作/分发外挂、修改器、封包工具 | 仅为理解协议做静态分析，不产出可用外挂 |
| 在非测试账号或他人账号上操作 | 仅限自有测试账号 |
| 公开 PoC / 在社区传播 | 仅私密上报厂商 |
| 未确认 EULA/法律与范围就动手 | 先确认授权与合法性再开始 |
